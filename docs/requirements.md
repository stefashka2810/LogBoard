# Требования LogBoard

## Назначение

LogBoard — клиентская часть системы для просмотра и анализа логов проектов. Приложение
работает в браузере, позволяет пользователю авторизоваться, управлять своими проектами,
участниками и API-ключами, а также просматривать, искать и анализировать логи.

## Пользователи системы

- разработчики;
- тестировщики;
- участники небольших проектных команд.

## Функциональные требования

### Публичная часть

- Система должна предоставлять публичную стартовую страницу с описанием продукта.
- Система должна предоставлять отдельную страницу лендинга.
- Система должна отображать основные возможности продукта, блоки с описанием и FAQ.
- Система должна предоставлять переходы к авторизации и регистрации.

### Авторизация и регистрация

- Система должна позволять пользователю зарегистрироваться по `username` и `password`.
- Система должна позволять пользователю войти в систему по `username` и `password`.
- Система должна выполнять клиентскую валидацию полей авторизации и регистрации.
- Система должна поддерживать подтверждение пароля при регистрации.
- Система должна позволять пользователю выйти из системы.
- Система должна проверять наличие активной пользовательской сессии при открытии
  соответствующих страниц.

### Защищённые маршруты

- Система должна ограничивать доступ к защищённым страницам для неавторизованных
  пользователей.
- Система должна перенаправлять неавторизованного пользователя на страницу входа.
- Система должна предоставлять защищённые страницы `dashboard` и страницы проекта.

### Работа с проектами

- Система должна отображать список проектов, в которых участвует пользователь.
- Система должна позволять создавать новый проект.
- Система должна позволять выбирать активный проект.
- Система должна сохранять выбранный проект в клиентском состоянии.
- Система должна отображать информацию о выбранном проекте.
- Система должна позволять удалять проект.

### Работа с участниками проекта

- Система должна отображать список участников проекта.
- Система должна позволять добавлять участника в проект.
- Система должна позволять изменять роль участника проекта.
- Система должна позволять удалять участника из проекта.
- Система должна ограничивать доступ к операциям управления участниками в зависимости
  от роли пользователя.

### Работа с API-ключами проекта

- Система должна отображать список API-ключей проекта.
- Система должна позволять создавать API-ключ проекта.
- Система должна позволять удалять API-ключ проекта.
- Система должна отображать данные API-ключей через интерфейс страницы проекта и
  связанные модальные окна.
- Система должна предоставлять пользователю инструкцию по интеграции проекта с
  использованием API-ключа.

### Работа с логами

- Система должна отображать логи выбранного проекта.
- Система должна предоставлять таблицу логов.
- Система должна поддерживать поиск по логам.
- Система должна поддерживать фильтрацию логов.
- Система должна поддерживать сортировку логов.
- Система должна поддерживать постраничную загрузку логов.
- Система должна отображать агрегированные показатели по логам.
- Система должна строить таймлайн логов по выбранному периоду.
- Система должна автоматически масштабировать временную аналитику в зависимости от
  выбранного периода.

### Дашборд

- Система должна предоставлять единый дашборд для работы с логами проекта.
- Система должна включать боковую панель с данными пользователя, списком проектов и
  действиями управления.
- Система должна включать блок фильтров логов.
- Система должна включать таблицу логов.
- Система должна включать блок аналитики и таймлайна.
- Система должна отображать состояние пустого дашборда, если проект или данные ещё не
  выбраны.

## Нефункциональные требования

### Архитектура и стек

- Клиентская часть должна быть реализована на `Next.js` с `App Router`.
- Пользовательский интерфейс должен быть реализован на `React` и `TypeScript`.
- Приложение должно быть организовано по принципам `Feature-Sliced Design`.
- Глобальное состояние должно управляться через `Redux Toolkit`.
- Серверные запросы должны быть реализованы через `RTK Query`.
- Переиспользуемое клиентское состояние должно сохраняться через `redux-persist`.
- Интерфейс должен использовать `Tailwind CSS` и UI-компоненты проекта.

### Работа с API и сессией

- Обмен данными с backend должен выполняться по HTTP/HTTPS через REST API с JSON.
- В development-режиме frontend должен поддерживать работу через rewrite `/api/*`.
- В production-режиме frontend должен уметь обращаться к backend по настроенному URL.
- Аутентификация должна быть построена на серверной сессии и cookie.
- Клиентская часть не должна хранить чувствительные access/refresh токены в Redux store.
- При истечении сессии система должна пытаться обновить её через `refresh`.
- При неуспешном обновлении сессии система должна очищать клиентское состояние и
  завершать пользовательскую сессию.

### UX и интерфейс

- Интерфейс должен быть доступен через современный веб-браузер без установки
  дополнительного ПО.
- Интерфейс должен быть адаптирован для типовых пользовательских сценариев работы с
  логами, проектами и участниками.
- Система должна отображать состояния загрузки и ошибок при работе с серверными
  запросами.
- Ключевые сценарии должны быть доступны через страницы, формы, таблицы и модальные
  окна.

### Качество и сопровождение

- Проект должен поддерживать unit-, component- и integration-тесты.
- Тесты должны выполняться с использованием `Vitest`, `Testing Library` и `jsdom`.
- Приложение должно быть подготовлено к контейнерному запуску через `Dockerfile` и
  `docker-compose.yml`.
